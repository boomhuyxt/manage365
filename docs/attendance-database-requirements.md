# Attendance database requirements

The backend never creates or alters tables at request time. Schema changes are delivered as reviewed SQL migrations. Shift creation and employee assignment remain separate business workflows.

## Required attendance schema

### `public.ca_lam`

Required columns: `id bigint`, `ngay_lam date`, `loai_ca`, `gio_bat_dau time`, `gio_ket_thuc time`, and `qua_dem boolean`.

### `public.dang_ky_ca`

Required columns: `id bigint`, `id_ca_lam bigint`, `id_nhan_vien bigint`, and `trang_thai`. Keep foreign keys to `ca_lam` and `nhan_vien`, plus a unique constraint on `(id_ca_lam, id_nhan_vien)`.

### `public.cham_cong`

| Column | Type | Requirement |
| --- | --- | --- |
| `id` | `bigint` | Primary key generated by PostgreSQL |
| `id_dang_ky_ca` | `bigint` | Nullable; FK to `dang_ky_ca(id)` when attendance belongs to a scheduled shift |
| `id_nhan_vien` | `bigint` | Not null; FK to `nhan_vien(id)` for every attendance record |
| `ngay_cham_cong` | `date` | Not null; local store attendance date |
| `gio_vao` | `timestamptz` | Not null |
| `gio_ra` | `timestamptz` | Nullable until check-out |
| `so_gio_thuc_te` | `numeric(5,2)` | Nullable until check-out |
| `phuong_thuc_cham_cong` | `varchar` or `text` | Backend writes `QR` |
| `trang_thai` | `varchar` or `text` | `CheckedIn` or `Completed` |
| `ghi_chu` | `text` | Nullable |
| `created_at` | `timestamptz` | Required/default recommended |
| `updated_at` | `timestamptz` | Required/default recommended |

Keep the unique constraint on `id_dang_ky_ca` for scheduled attendance. Also keep the partial unique index on `(id_nhan_vien, ngay_cham_cong) WHERE id_dang_ky_ca IS NULL` so an employee cannot create two unscheduled records on the same day.

The reviewed migration is [`sql/001_allow_unassigned_attendance.sql`](sql/001_allow_unassigned_attendance.sql).

## GPS/geofence schema

Apply [`sql/002_add_attendance_geofence.sql`](sql/002_add_attendance_geofence.sql). It enables PostGIS in the `extensions` schema and creates:

- `public.dia_diem_cham_cong`: real shop coordinates and allowed radius.
- `public.vi_tri_cham_cong`: immutable GPS evidence for each `CHECK_IN` and `CHECK_OUT`.

Configure `STORE-01` with exact coordinates measured at the shop using [`sql/003_configure_store_location.example.sql`](sql/003_configure_store_location.example.sql). PostGIS `ST_MakePoint` takes longitude first and latitude second.

The backend calculates distance with `ST_Distance`. Mobile clients must never be trusted to calculate or submit their own distance.

## Behavior before shift scheduling is available

- QR verification returns an option named `Chấm công chưa xếp ca` with `shiftAssignmentId: null`.
- Check-in creates `cham_cong` with `id_dang_ky_ca = NULL`, while `id_nhan_vien` and `ngay_cham_cong` remain mandatory.
- Check-out updates that same row.
- When shift scheduling is implemented, scheduled attendance continues using `id_dang_ky_ca`.
- The admin dashboard reads both scheduled and unscheduled records from PostgreSQL.

## Required indexes

- `dang_ky_ca(id_nhan_vien, trang_thai)`
- `ca_lam(ngay_lam)`
- `cham_cong(id_dang_ky_ca)`
- `cham_cong(id_nhan_vien, ngay_cham_cong desc)`
- Partial unique index for unscheduled attendance described above

## Database member checklist

1. Keep the migration in the database migration history and apply it consistently in every environment.
2. Verify all existing `cham_cong` rows were backfilled with `id_nhan_vien` and `ngay_cham_cong` before the columns became not null.
3. Do not make `id_dang_ky_ca` mandatory again; `NULL` represents attendance before scheduling is implemented.
4. Preserve the foreign keys and duplicate-protection indexes.
5. When the scheduling feature is ready, create `ca_lam` and `dang_ky_ca` through an admin workflow, not from the attendance repository.
6. Grant the application role `SELECT` on employee/shift tables and `SELECT`, `INSERT`, `UPDATE` on `cham_cong`.
7. Do not commit database passwords or production seed data.
8. Measure and configure the exact shop latitude/longitude before enabling production attendance.
9. Keep PostGIS in the `extensions` schema and preserve the GIST indexes created by migration `002`.
10. Treat `vi_tri_cham_cong` as attendance evidence; do not let mobile clients write to it directly.
