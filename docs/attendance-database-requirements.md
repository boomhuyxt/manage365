# Attendance database requirements

The backend does not create or alter tables, seed shifts, or assign shifts to employees. Database structure and business data must be prepared through reviewed migrations or an administration workflow.

## Required tables

### `public.ca_lam`

Required columns used by the API:

| Column | PostgreSQL type | Requirement |
| --- | --- | --- |
| `id` | `bigint` | Primary key; generated by the database |
| `ngay_lam` | `date` | Not null |
| `loai_ca` | `varchar` or `text` | Not null |
| `gio_bat_dau` | `time` | Not null |
| `gio_ket_thuc` | `time` | Not null |
| `qua_dem` | `boolean` | Not null, default `false` |

For a normal shift, `gio_ket_thuc` must be later than `gio_bat_dau`. A shift crossing midnight must have `qua_dem = true`.

### `public.dang_ky_ca`

| Column | PostgreSQL type | Requirement |
| --- | --- | --- |
| `id` | `bigint` | Primary key; generated by the database |
| `id_ca_lam` | `bigint` | Foreign key to `ca_lam(id)` |
| `id_nhan_vien` | `bigint` | Foreign key to `nhan_vien(id)` |
| `trang_thai` | `varchar` or `text` | `Approved`, `Pending`, or a business-defined rejected/cancelled state |

Create a unique constraint on `(id_ca_lam, id_nhan_vien)` so an employee cannot be assigned to the same shift twice.

### `public.cham_cong`

| Column | PostgreSQL type | Requirement |
| --- | --- | --- |
| `id` | `bigint` | Primary key; generated by the database |
| `id_dang_ky_ca` | `bigint` | Not null, unique, foreign key to `dang_ky_ca(id)` |
| `gio_vao` | `timestamptz` | Not null |
| `gio_ra` | `timestamptz` | Nullable until check-out |
| `so_gio_thuc_te` | `numeric(5,2)` or compatible | Nullable until check-out |
| `phuong_thuc_cham_cong` | `varchar` or `text` | Backend writes `QR` |
| `trang_thai` | `varchar` or `text` | Backend writes `CheckedIn` or `Completed` |
| `ghi_chu` | `text` | Nullable |
| `created_at` | `timestamptz` | Not null/default recommended |
| `updated_at` | `timestamptz` | Not null/default recommended |

The unique constraint on `id_dang_ky_ca` is required for atomic duplicate check-in protection.

## Required indexes

- `dang_ky_ca(id_nhan_vien, trang_thai)`
- `ca_lam(ngay_lam)`
- `cham_cong(id_dang_ky_ca)` (the unique constraint may provide this index)
- An index supporting attendance history, for example `cham_cong(gio_vao desc)`

## Roles and employee data

- Ensure `public.vai_tro` contains exactly the application role names `Admin`, `Manager`, and `Employee`.
- Assign the correct `nhan_vien.id_vai_tro` value. JWT authorization depends on `vai_tro.ten_vai_tro` matching those names exactly.
- Create shifts in `ca_lam` through migration, an admin API, or an administration screen.
- Assign employees through `dang_ky_ca`. The attendance API will no longer assign every employee to every shift automatically.
- Do not seed production data from the API. Test seed data belongs in a separate development/test migration.

## Database permissions

The application database role needs:

- `SELECT` on `nhan_vien`, `vai_tro`, `ca_lam`, and `dang_ky_ca`.
- `SELECT`, `INSERT`, and `UPDATE` on `cham_cong`.
- Sequence `USAGE`/`SELECT` where identity or serial sequences require it.

Prefer a dedicated least-privilege application role instead of the Supabase `postgres` owner account.

## Delivery checklist for the database member

1. Inspect the existing Supabase schema and compare every required column and type above.
2. Create a versioned migration for missing constraints, indexes, and role rows.
3. Back up the affected tables before applying changes to production.
4. Apply and verify the migration first in a non-production environment.
5. Create at least one current-day shift and one `Approved` assignment for an employee used in API testing.
6. Verify check-in creates one `cham_cong` row, duplicate check-in is rejected, and check-out updates that same row.
7. Provide the backend team with the migration version and confirmation that the schema is ready; do not send database passwords through Git or chat.
